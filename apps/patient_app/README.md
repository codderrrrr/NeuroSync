# NeuroSync — Patient App (Flutter)

The patient-facing application for NeuroSync. After sign-in the app is a
bottom-navigation shell with three decoupled modules:

```text
Splash / session check
        ↓
  signed out ──► Login ──► Signup
        ↓
  ┌──────────────────────────────────────────┐
│  MainShell (bottom navigation)         │
│                                          │
│  Home          Check-ins      Doctors    │
│  profile +     record & view  link list  │
│  log out       check-ins      + add code │
└──────────────────────────────────────────┘
```

Check-ins are the patient's raw symptom ratings, stored and shown exactly as
reported; the app performs no scoring or interpretation. No medication or
clinical interpretation screens exist yet.

## Prerequisites

- Flutter SDK (stable) with Dart 3.5+
- A running NeuroSync API (see the repository root `README.md`)
- PostgreSQL migrated to `head` (`uv run alembic upgrade head`)

## First-time setup

The platform folders (`android/`, `ios/`, …) are generated by Flutter and are
not committed. Generate them once inside this directory:

```bash
cd apps/patient_app
flutter create --project-name neurosync_patient --platforms=android,ios .
flutter pub get
```

`flutter create` will not overwrite the existing `lib/`, `test/` or `pubspec.yaml`
contents; it only adds the missing platform scaffolding.

## Running

The API base URL is compiled in, so point the build at your API:

```bash
# Android emulator (10.0.2.2 is the host machine)
flutter run --dart-define=NEUROSYNC_API_BASE_URL=http://10.0.2.2:8000

# iOS simulator / desktop
flutter run --dart-define=NEUROSYNC_API_BASE_URL=http://localhost:8000

# Physical device (use your machine's LAN address)
flutter run --dart-define=NEUROSYNC_API_BASE_URL=http://192.168.1.10:8000
```

Seed a development doctor and code so the linking flow can be exercised:

```bash
cd ../..                       # repository root
uv run python -m neurosync.scripts.seed_doctor "Dr. Development" ABC123
```

## Architecture

```text
presentation (screens/widgets)
        ↓
state (ChangeNotifier controllers)
        ↓
repository (feature data access)
        ↓
ApiClient (base URL, bearer token, JSON, errors)
```

- `lib/core/` — configuration, HTTP client, theme, shared widgets, token storage
- `lib/features/auth/` — models, repository, controller, screens
- `lib/features/check_ins/` — models, repository, controller, screens
- `lib/features/doctor_links/` — models, repository, controller, screens
- `lib/features/home/` — patient home screen (account + log out)
- `lib/features/shell/` — the signed-in bottom-navigation shell

Controllers are provided through `AppScope` (an `InheritedWidget`) and widgets
subscribe with `ListenableBuilder`, so rebuilds stay scoped to what changed.

### Efficiency notes

- One shared `http.Client` per application run, so connections are reused.
- The session token is cached in memory (`SessionTokenCache`) and only read from
  secure storage on launch and on sign-in/sign-out, never per request.
- `GET /auth/me` is called exactly once per launch to validate the stored session.
- A successful link request prepends the link the server returned instead of
  re-fetching the whole list.
- A saved check-in does the same: the server's row (id, timestamp) is prepended
  to the history without a re-fetch, and `recorded_at` is stamped server-side.

### Session handling

The session token is returned in the login/signup response body and kept in
platform secure storage (`flutter_secure_storage`). Requests send it as
`Authorization: Bearer <token>`, which is the appropriate mechanism for a mobile
client. The API also sets an HttpOnly cookie for browser clients; this app does
not rely on it.
